# implement

このスキルが利用者の入口。利用者は引数なしで `$implement` と入力する。自然文の「実装してください」でも、このスキルが選ばれたら同じ手順で進める。会話で特定の対象が明示された場合は、その指定を優先する。

`.codex/agents/implementation-orchestrator.toml` のカスタムエージェントを起動し、会話上の制約を渡す。オーケストレーターが開いている Issue と関連 PR から既存の未完了対象を収集し、各 Issue の本文を読んで仕様と受け入れ基準を確認してから一件ずつ処理する。本文に仕様書パスがあればそのファイルを読む。パスがなくても本文に実装可能な仕様が記載されていれば、本文を仕様として使う。パスの欠落だけを理由に対象から外さない。起動手段がカスタムエージェント名の選択に対応しない場合は、このファイルの `developer_instructions` を読み、親スレッドがオーケストレーターを担当する。実装や評価を親スレッドが兼ねない。

オーケストレーターは `.codex/agents/codex-implement.toml` と `.codex/agents/evaluator.toml` の役割を**別々のサブエージェントスレッド**で起動し、実装 → 独立評価 → 指摘修正の順に進める。実装者は `gpt-6-luna`、評価者は `gpt-6-sol` を使う。エージェント名を選べない起動手段では、各 TOML の指示を対応するスレッドへの依頼文に含め、起動時のモデルも指定する。別スレッドを起動できない場合は、独立評価を実施したとは報告せず、利用者に制約を伝える。Codex CLI を外部プロセスとして起動しない。

独立評価が PASS なら、その対象の変更をコミット・プッシュし、すぐに PR を作成する。同じ対象の PR が既にあれば更新し、重複して作らない。PR には対応する Issue、変更内容、実行したチェック、独立評価の結果を記載する。PR の作成に失敗した場合は理由を報告する。

PR を作成・更新したら未処理の開いている Issue を確認し、実装可能な Issue が残っていれば直ちに次の実装に着手する。対応済みの Issue や作成した PR を再処理しない。着手可能な Issue がなくなるまで、実装 → 独立評価 → PR 作成を順に続ける。

利用者にはオーケストレーターの最終報告を返す。
