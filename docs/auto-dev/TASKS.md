# 自動開発タスクキュー

`.github/workflows/auto-dev.yml` が参照するタスクリスト。
Claude Codeがこのファイルを上から順に読み、`### [ ]` の未完了タスクを1件実装・コミット・pushしたら、
そのまま次の未完了タスクに進む――というのを、未完了タスクがなくなるか、その回の実行時間・トークンを
使い切るまで繰り返す(1回の実行で1件とは限らない)。

## 使い方

- タスクは1見出しにつき1件、下の書式で追加する
- 完了したタスクは自動実行によって `### [x]` に書き換えられ、コミットされる
- `npm run check` を通せず自動実装を断念したタスクは `### [!]` に書き換えられ、
  対応するIssueが作成される。自動実行の対象から外れるので、原因を解消してから
  手動で `### [ ]` に戻すこと
- 優先度の高いタスクほど上に置く
- ファイルが肥大化しないよう、**タスクは直近30件までとし、31件目以降(古い完了済みタスク)は
  削除する**。削除したタスクの内容はgit履歴(`git log -p docs/auto-dev/TASKS.md`)から参照できる
- 大きすぎるタスクは1回の自動実行(1コミット)で完結しないことがあるため、小さく分割する

## 書式

```
### [ ] タスクのタイトル

- 背景・目的
- 実装してほしい内容(受け入れ条件)
- 関連ファイル・参考情報(あれば)
```

### [x] 依存の矢印が途切れたり逆向きに回り込んだりするのを直す

- 背景・目的: 中級1「循環依存を断ち切る」などで、矢印がどこからどこへ向かっているのか読めない。
  学習の手がかりになる「赤い矢印(循環依存)」が見づらいと、ステージの狙いが伝わらない。
  - 左向きの依存(例: `Customer → Order`)が、Customerの右端から出てOrderの左端に入るため、
    ファイルの箱の裏を大きく回り込み、途中が隠れて「右端に短い赤線」「左端に矢じりだけ」のように見える
  - 双方向の依存(`Order → Customer` と `Customer → Order`)が同じ経路に重なり、1本に見える
  - 矢印がファイルノード(親)の下に描かれ、箱と重なる部分が隠れる
- 原因: `ClassNode.tsx` のハンドルが target=左・source=右 で固定されていること、
  エッジの重なり順(zIndex)を指定していないこと
- 実装してほしい内容(受け入れ条件):
  - クラスノードの左右両方に source/target のハンドルを置き(id で区別)、`dependencyEdges` で
    ノードの位置関係から「向かい合う側」のハンドルを選ぶ(右にあるクラスへは右→左、左にあるクラスへは左→右)。
    位置は `layoutCodebase` の結果から求める。純粋関数にしてVitestでテストを書く(TDD)
  - 双方向の依存は2本が重ならないよう、上下にずらすかカーブを変えて別の線として見えるようにする
  - エッジをファイルノードより手前に描く(React Flowのエッジの `zIndex` など標準機能で)
  - 中級1のステージで、赤い矢印が途切れず両端のクラスにつながって見えることをスクリーンショットで確認する
  - 既存の依存矢印のE2E(メソッド移動でつなぎ変わる)が通ること
- 関連ファイル: `src/presentation/canvas/layoutCodebase.ts`(`dependencyEdges`)、
  `src/presentation/canvas/ClassNode.tsx`、`src/presentation/canvas/CodebaseCanvas.tsx`

### [ ] 修正が必要なファイルにエラーマーク・危険マークを付ける

- 背景・目的: 画面上部の点数(例: 60点)だけでは、どのファイルから手を付ければよいか分からない。
  ファイルの箱に印を付け、「直すべき場所」と「特に悪い場所」をひと目で分かるようにしたい。
- 実装してほしい内容(受け入れ条件):
  - `src/domain/scoring/` に、ファイルごとの減点を求める純粋関数を追加する(TDD、既存の
    `findLineLimitViolations`・`findResponsibilityViolations`・`classDependencies` を再利用し、減点の計算を重複させない)
    - 違反はそれが属するファイルに数える: 行数(メソッド・クラス・ファイル)と責務の混在はその持ち主のファイル、
      結合度と循環依存は依存元(`from`)のクラスがあるファイル
    - 全ファイルの減点を足すと `scoreCodebase` の減点の合計と一致すること(テストで確認)
  - ファイルノード(`FileNode.tsx`)のヘッダーに印を出す
    - 減点が1件以上あるファイル: エラーマーク
    - そのファイルの減点が大きいファイル(暫定で30点以上。しきい値は定数にまとめる): エラーマークの代わりに危険マーク
    - 違反のないファイルには何も出さない
    - 色だけに頼らず、アイコン+`aria-label`/`title`(例: 「修正が必要」「危険: -30点」)で意味が伝わるようにする
    - セマンティックズームで詳細を隠している倍率でも、印は表示する(どこが悪いかは引いて見たときこそ知りたい)
  - リファクタリング(抽出・移動など)で違反が解消されたら、その場で印が消える・変わることをE2Eで確認する
- 関連ファイル: `src/domain/scoring/score.ts`、`src/presentation/canvas/FileNode.tsx`、
  `src/presentation/canvas/semanticZoom.ts`

### [ ] ステージの行数を実業務の規模に合わせる

- 背景・目的: 今のステージはメソッドが5〜34行、処理のまとまり(Fragment)が2〜12行、メソッドの上限が15行と小さすぎる。
  実業務では100行を超えるメソッドも珍しくなく、「長すぎて読めないメソッドを分解する」という
  現場の感覚が伝わらない。プレイヤー(新卒〜4年目)が職場で出会う規模に合わせたい。
- 実装してほしい内容(受け入れ条件):
  - `src/infrastructure/stages/` の全ステージ(チュートリアル・初級・中級)の Fragment の `lines` と `limits` を実業務の規模に引き上げる。目安:
    - 分解前の「太ったメソッド」: 80〜150行
    - Fragment: 10〜40行(メソッド呼び出し `responsibility: 'call'` の行は1行のまま)
    - 上限: メソッド 30〜50行、クラス 200〜300行、ファイル 300〜400行(ステージの難しさに応じて調整)
  - どのメソッド・クラス・ファイルが上限を超えるか(=各ステージの狙いと初期の点数)は今と変えない。
    数値を一律に掛け算するのではなく、Fragment ごとに内容(「PDFを描画する」は長い、「合計を求める」は短い、など)に見合った行数にする
  - 抽出・移動で正しく分解すれば、全メソッド・クラス・ファイルが上限内に収まる(クリアできる)ことを確認する
  - `stageCatalog.test.ts` に「各ステージに80行以上のメソッドが1つ以上ある」「上限は method < class < file の順」のテストを追加する(TDD)
  - 行数を前提にしているユニットテスト・E2E(初期点数の `行数 -10` など)が通ること。3桁の行数でもメソッドのチップ・バッジの表示が崩れないことをスクリーンショットで確認する
  - ステージの目標文(`goal`。「メソッドは15行以内」など行数が書かれている)と説明文(`description`)を新しい上限に合わせて直す
- 関連ファイル: `src/infrastructure/stages/tutorialStages.ts`、`beginnerStages.ts`、`intermediateStages.ts`、
  `src/infrastructure/stages/stageCatalog.test.ts`、`e2e/`

### [ ] ファイルとクラスの名前を変更(Rename)できるようにする

- 背景・目的: 「クラスを追加」「ファイルを追加」で作った受け皿や、責務に合わない既存の名前を付け直せない。
  名前付けもリファクタリングの大事な一部なので、ファイルのパスとクラス名を変えられるようにしたい。
- 実装してほしい内容(受け入れ条件):
  - `src/domain/codebase/` に純粋関数 `renameClass(codebase, classId, newName)` と `renameFile(codebase, fileId, newPath)` を追加する(TDD、`Result`型)
    - 前後の空白は取り除く。空の名前・重複する名前はエラーにする(`addClass`・`addFile` と同じ規則。重複チェックは共通化して再利用する)
    - 同じ名前への変更は、エラーにせず元のままの Codebase を返す
    - 存在しない ID はエラーにする
  - `application/RefactorUseCases.ts` にユースケースとエラーメッセージ(`describe...Error`)を追加し、ストアから呼ぶ
  - 画面: クラス・ファイルの右クリックメニューに「名前を変更」を追加し、今の名前が入った入力欄で確定(Enter)・取り消し(Escape)できるようにする。
    失敗したときは既存の操作と同じくメッセージを出す
  - キーボードだけでも操作できること(右クリックメニューを開いて項目を選べる、など)
  - E2E: クラス名とファイルのパスを変更すると、キャンバスの表示が変わる。重複した名前ではエラーメッセージが出て名前は変わらない
- 関連ファイル: `src/domain/codebase/addClass.ts`、`addFile.ts`、`src/presentation/canvas/CanvasContextMenu.tsx`、
  `src/presentation/store/useGameStore.ts`

### [ ] Ctrl+Z / Ctrl+Y で操作の取り消し・やり直しをできるようにする

- 背景・目的: 今は間違えたら「やり直す」でステージの最初に戻るしかない。1手ずつ戻したり進めたりして、
  「この移動で点数がどう変わったか」を試せるようにしたい。
- 実装してほしい内容(受け入れ条件):
  - Codebase を変える操作(抽出・統合・メソッド移動・クラス移動・クラス追加・ファイル追加・名前の変更)を1手として記録し、
    Ctrl+Z で1手戻す、Ctrl+Y(と Ctrl+Shift+Z)で1手進める。Mac では Cmd でも動くようにする
  - Codebase は変更しない純粋関数で作り直しているので、履歴は Codebase のスナップショットを過去・未来の2つの配列に積むだけでよい
    (差分や操作の逆算は作らない)。履歴を積む・戻す・進める処理は純粋関数にしてVitestでテストを書く(TDD)
    - 失敗した操作(`Result` がエラー)は履歴に積まない
    - 新しい操作をしたら「進める」側の履歴は捨てる
    - ステージを切り替えたら履歴を空にする。「最初に戻す」(ステージの最初に戻す)は1手として記録し、Ctrl+Z で戻せるようにする
  - 今の「やり直す」ボタン(`src/presentation/stage/StagePanel.tsx`)は、Ctrl+Y の「やり直し」と紛らわしいので「最初に戻す」に改名する
    (ボタン名を参照しているE2Eがあれば合わせて直す)
  - 戻した結果、選択中のメソッドがなくなったら選択を外す
  - 入力欄(名前の入力など)にフォーカスがあるときは、ブラウザ標準の文字の取り消しを優先し、Codebase の取り消しはしない
  - 画面上部に「元に戻す」「やり直し」のボタンも置き、戻せない・進められないときは無効にする(ショートカットを知らない人・キーボードを使わない人のため)
  - E2E: メソッドを別クラスへドラッグで移したあと Ctrl+Z で元のクラスに戻り、Ctrl+Y で再び移動先に戻る
- 関連ファイル: `src/presentation/store/useGameStore.ts`、`src/presentation/App.tsx`、`src/presentation/stage/StagePanel.tsx`
