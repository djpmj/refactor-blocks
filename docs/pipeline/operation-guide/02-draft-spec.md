# 仕様草案: 画面上部から開ける「操作ガイド」(今ある操作と、キーボードでの代わりの操作の一覧)

- slug: `operation-guide`
- 元になった探索: `docs/pipeline/operation-guide/01-discovered.md`
- 前例: `src/presentation/preview/CodebasePreviewDialog.tsx`(ネイティブ `<dialog>`)、`e2e/preview.spec.ts`

## 1. 背景・目的

- リファクタリング画面の操作の多くは画面のどこにも書かれていない。右クリックメニュー(クラス・ファイルの追加/名前の変更/継承元/削除/移動)、
  ダブルクリックでの名前の変更、余白へのドロップで新しいクラス/ファイルを作る操作、Shift+F10 でメニューを開く操作は、
  知らなければ見つからない。初級2の goal「『クラスを追加』で受け皿を作ろう」の時点で手が止まりうる。
- キーボードでの代わりの操作(Shift+F10・メニュー内の Tab/Enter・Ctrl+Z/Y)は**用意されているのに知る手段が無い**。
  CLAUDE.md の ponytail で「手を抜かないもの」に挙がるアクセシビリティ(キーボード操作を含む)の穴になっている。
- ヒント(`HintPanel.tsx`)を開くと模範解答の手順まで見えてしまうので、「操作のやり方だけ知りたい」ときの逃げ場にならない。

**本当に新しい仕組みが要るか**: 操作そのものは作らない(すべて既存)。要るのは「一覧を見せる画面1つ」だけで、
ネイティブの `<dialog>`(`showModal()` で Esc・背景の上乗せ・フォーカストラップ・閉じたときのフォーカス復帰をブラウザに任せる)と
`<form method="dialog">`(閉じるボタンをJSなしで実装できるHTML標準)で足りる。ストア・状態管理・新しい依存は不要。
開閉の状態も React の state に持たず、`useRef` で dialog 要素の `showModal()` を呼ぶだけにする。

## 3. データ/型の変更

ドメインモデル・永続化スキーマ・ストアの変更は無し。`OperationGuide.tsx` の中だけで使う型を1つ置く。

```ts
/** ガイドの表の1行。keyboard が null の操作は「—(マウスのみ)」と表示する。 */
type GuideRow = {
  readonly task: string;          // やりたいこと(例: 「メソッドを別のクラスへ移す(Move Method)」)
  readonly mouse: string;         // マウスでのやり方
  readonly keyboard: string | null; // キーボードでのやり方
};
```

### 内容をデータ(配列)で持つ理由

JSXに直書きすると表の行だけで1関数60行(`eslint.config.js` の `max-lines-per-function`)を超える見込みのため、
**ファイル内の定数配列 `GUIDE_ROWS: readonly GuideRow[]` + `map`** で書く。別ファイルには分けない
(使うのはこのコンポーネントだけ)。配列の先頭に、未決事項4で決めた保守のためのコメントを書く。

### コンポーネントの形

- `export function OperationGuide()` がボタンと `<dialog>` の両方を返す(`<>...</>`)。props なし
- ボタン: `<button type="button" aria-haspopup="dialog" data-testid="open-operation-guide">操作ガイド</button>`。
  **`aria-pressed` は付けない**(`color-contrast-a11y` が `.mode-switch button[aria-pressed="true"]` の色を変える予定のため、その影響を受けない)。
  押したら `dialogRef.current?.showModal()`(既に開いていれば何もしない。`open` を見る)
- ダイアログ: `<dialog ref={dialogRef} className="operation-guide" aria-labelledby="operation-guide-title" data-testid="operation-guide">`
  - 見出し `<h2 id="operation-guide-title">操作ガイド</h2>`
  - 閉じるボタン: `<form method="dialog"><button aria-label="閉じる">✕</button></form>`(`CodebasePreviewDialog` と同じ見た目・アクセシブルネーム)。
    `showModal()` 直後はブラウザがダイアログ内の最初のフォーカス可能要素(この閉じるボタン)にフォーカスを入れる
  - 本文: 下記の表と補足。スクロールはダイアログ自身の `overflow: auto` に任せる
  - `<dialog>` は常にマウントしておく(閉じている間はブラウザが非表示にする)。`CodebasePreviewDialog` のように条件付きで
    アンマウントしないのは、アンマウントだと閉じたときのフォーカス復帰がブラウザに任せられないため
- 閉じたときのフォーカス: ネイティブの dialog は `showModal()` 前にフォーカスしていた要素(=「操作ガイド」ボタン)へ戻す。
  **E2Eで戻らないと分かった場合に限り**、`<dialog onClose>` でボタンへ `focus()` する1行を足す(それ以上の自前実装はしない)

**実装時点の** `CanvasContextMenu.tsx` の `menuItemsFor` のラベル・`MethodEditor.tsx` のボタン名をそのまま引用して書く

表の下に補足を短く書く(各1〜2文):

- **Shift+F10**: メソッド・フィールド・クラスの見出し・ファイルにフォーカスしてから押すと右クリックメニューが開く(キーボードのメニューキーでも可。Mac には対応キーが無い)。
  メニューの中は Tab で移動、Enter で決定、Esc で閉じる
- **縮小するとメソッドが隠れる**: 倍率が 60% 未満になるとメソッドと行数を隠し、ファイル名とクラス名だけにする(`semanticZoom.ts` の `DETAIL_ZOOM`。
  数値は定数を import して文言に埋め込まず、「60%」と書いてよい。定数が変わったときの追従は未決事項4の運用に含める)
- **白紙設計・変更依頼の実装中**: キャンバスの操作は同じ(未決事項2)

### キーボード列に書いてよいもの

**既存のE2Eで守られている操作**(メソッド/フィールドのチップでの Shift+F10、メニュー内の Tab/Enter/Esc、Ctrl+Z/Y、モード切り替えの Enter)か、
**実装者が実機(Chromium)で確かめた操作**だけを書く。確かめて効かなかったものは「—(マウスのみ)」とし、**直さずに**PRの説明に書く
(直すのはこの仕様のスコープ外)。草案時点で要確認なのは次の3つ:

1. クラスの見出し・ファイルの箱にフォーカスして Shift+F10(dnd-kit の `attributes` / React Flow のノードの `tabIndex` でフォーカスはできる見込み)
2. メソッドのチップにフォーカスして Enter/Space で選択(メソッドエディタに出る)できるか。dnd-kit の `KeyboardSensor` が Space/Enter を
   ドラッグ開始として先に取る可能性があり、効かない見込みが高い。効かなければ「—(マウスのみ)」
3. 未決事項3で `KeyboardSensor` を案内する場合、その手順

## 未決事項

### 未決事項1: 「操作ガイド」ボタンをどこに置くか

- 選択肢A(推奨): モード切り替えの `<nav className="mode-switch">` の中の末尾に置き、右寄せにする。既存の `.mode-switch button` の見た目がそのまま効くのでCSSは右寄せ1行で済み、`App.tsx` の変更も1行。ただし `aria-label="モード"` のナビゲーションの中に「モードではないボタン」が1つ混ざる
- 選択肢B: `<nav>` の外(兄弟要素)に置き、`nav` とボタンを `<header className="app__top">` のような横並びの入れ物で包む。ランドマークの意味は正しくなるが、`.mode-switch` の背景・余白を入れ物側へ移す(既存CSSの書き換え)か、入れ物用のCSSを数行足す必要があり、`color-contrast-a11y` と同じあたりのCSSに触れる

### 未決事項2: どの画面の操作を載せるか

- 選択肢A(推奨): リファクタリング画面の操作を表にし、「白紙設計・変更依頼の実装中もキャンバスの操作は同じ(部品を余白へドラッグすると新しいクラスができる)」と補足を1行書く。両モードとも同じ `CodebaseCanvas` を使っており操作が同じなので、表を増やさずに済む
- 選択肢B: リファクタリング画面の操作だけ。白紙設計・変更依頼の案内は各パネルの既存の説明文(`BlankDesignPanel.tsx`・`ChangeRequestPanel.tsx`)に任せる
- 選択肢C: モードごとに見出しを分けて、それぞれの操作を載せる(設計くらべ・白紙設計・変更依頼)。網羅的だが、ほとんどが同じ内容の繰り返しになる

### 未決事項3: dnd-kit の `KeyboardSensor`(Space で掴む・矢印キーで動かす・Space で置く・Esc で取り消し)をガイドに書くか

右クリックメニューで代わりができない「クラスを別のファイルへ移す」「新しいクラス/ファイルへ移す」の、今のところ唯一のキーボード手段。
ただし既存のE2Eで守られておらず、矢印1回の移動量が画面の座標しだいなので、ズーム・パンによっては目的のファイルや余白まで届きにくい
(`move-class-via-context-menu/01-discovered.md` の既知の弱点)。

- 選択肢A(推奨): 補足として書く。表のキーボード列は右クリックメニューの手順を先に書き、メニューで代わりのできない3行だけ「見出し/メソッドにフォーカス → Space で掴む → 矢印キーで動かす → Space で置く(Esc で取り消し)。遠くへは運びにくい」と書く。実装者が実機で確かめ、効かなければ「—(マウスのみ)」にする
- 選択肢B: 書かない。確実に使える右クリックメニューの手順だけを案内し、該当3行は「—(マウスのみ)」にする。未検証の操作を案内しないが、キーボード利用者はクラスを移す手段が無いと受け取る

### 未決事項4: 後から操作が増えたとき(`move-class-via-context-menu` のマージなど)、ガイドをどう追従させるか

草案時点で `move-class-via-context-menu`(右クリックメニューに「別のファイルへ移動」を足す)が進行中。どちらが先にマージされても、
**この実装では「実装時点でマージ済みの操作」だけを書く**(未マージの操作は書かない)。そのうえで今後の運用を決める。
