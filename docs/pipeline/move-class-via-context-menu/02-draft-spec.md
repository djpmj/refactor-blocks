# 仕様草案: 右クリックメニューから移動先のファイルを選んでクラスを移す

- slug: `move-class-via-context-menu`
- 元になった探索: `docs/pipeline/move-class-via-context-menu/01-discovered.md`
- 前例: `docs/pipeline/move-via-context-menu/04-final-spec.md`(メソッド/フィールドの「別のクラスへ移動」)、同 `06-evaluation.md`

## 1. 背景・目的

- `move-via-context-menu` で、メソッド・フィールドはキーボードだけ(Shift+F10 → Tab/Enter)で別クラスへ移せるようになった。
  一方、**クラスを別ファイルへ移す操作(Move Class)は、クラスのヘッダーを dnd-kit でドラッグするしかない**。
  キーボードでは `KeyboardSensor` で運ぶことになり、ズーム・パンの状態しだいで目的のファイルまで届かないうえ、
  スクリーンリーダーからは移動先の候補も分からない。
- 「ファイル分け」はこのゲームの3本柱の1つで、模範解答(中級2「何でも入った services.ts」)でも Move Class を使う。
  CLAUDE.md の ponytail で「手を抜かないもの」にアクセシビリティ(キーボード操作を含む)があり、主要なリファクタリング操作のうち
  クラスの移動だけが取り残されている。

**本当に新しい仕組みが要るか**: 要らない。移動そのものは既存のストア操作 `moveClass(classId, targetFileId)`
(`apply` 経由なので Undo・エラー表示もそのまま効く)を呼ぶだけ。メニューの部品も既存の `SubmenuTrigger` と、
前回作った `MoveMenuItem` と同じ形を使う。右クリックの対象判定(`ContextMenuTarget` の `classId` / `member`)と
フォーカス復帰(`returnFocus` / `dismiss`)も前回のものがそのまま使える。新しく要るのは
「移動先ファイルの候補一覧」と「その候補を並べるサブメニュー1つ」だけ。

## 3. データ/型の変更

ドメインモデル・永続化スキーマ・`ContextMenuTarget` の変更は無し。

### 右クリックした要素の判定(既存のまま)

クラスのヘッダーを右クリック(または Shift+F10)すると、今どおり `onNodeContextMenu` に届き、
`classId` = そのクラス、`fileId` = そのファイル、`member` = null になる(ヘッダーには `data-method-id` / `data-field-id` が無いため)。
「別のファイルへ移動」はこの **`classId !== null && member === null`**(= クラスのヘッダーを右クリックしたとき)にだけ出す
(未決事項2で選択肢Bになった場合は `classId !== null` のとき)。

### メニュー項目

- `MenuItem` に `{ kind: 'move-class-submenu'; label: '別のファイルへ移動' }` を足す。
  ラベルはヘッダーの `aria-label`(「<クラス名> を別ファイルへ移動」)と揃えた言い回しにする。
- 置き場所は未決事項1で決める(推奨は先頭)。
- `MoveClassMenuItem` は `MoveMenuItem` と同じ形で書く:
  - 候補(`moveClassTargets` の結果)をファイルのパス(`file.path`)のボタン(`role="menuitem"`)で並べる。サブメニューは `role="menu"`、`aria-label` は項目名
  - 押したら `moveClass(target.classId, file.id)` を呼び、`onClose()` でメニューを閉じる(フォーカスは戻さない。前回と同じ)
  - 候補が0件(ファイルが1つしか無い)なら項目自体を出さない(`null` を返す)。先頭項目へのフォーカスは既存の
    `MenuItems` の `useLayoutEffect`(実際に描画された先頭の menuitem へフォーカス)がそのまま効く
- 候補の並び順は `codebase.files` の順(キャンバスのレイアウト順)。前回の「ファイル順・宣言順」と揃える。パスでの並べ替えはしない
- クラスが1つも無いファイルも候補に含める(「ファイルを追加」してからクラスを移す、が模範解答どおりの主な使い方のため)
- `ExtendsMenuItemProps` を `MoveMenuItem` / `MoveClassMenuItem` でも使うことになるので、型名を `SubmenuItemProps` に改める
  (`06-evaluation.md` の指摘4。同じ箇所を触るので今回まとめる。中身は変えない)

### キーボードでメニューを開く

追加コードは書かない(前回の確定どおりブラウザ標準に任せる)。クラスのヘッダーは dnd-kit の `attributes`
(`tabIndex=0`、`role="button"`)でフォーカスでき、フォーカス中に Shift+F10 / ContextMenu キーを押すと
ブラウザが `contextmenu` を出し、既存の `onNodeContextMenu` で開く。E2Eで `press('Shift+F10')` が効くことを確かめる。
**効かなければ実装者は独自実装(ヘッダーの `onKeyDown` で拾う等)に進まず報告する。** macOS は今回も対象外。

### メニューを閉じたときのフォーカス(既存のまま)

- Escape・外側クリックで閉じたときは、開く前にフォーカスしていた要素(クラスのヘッダー)へ戻る(既存の `dismiss`)
- 移動を実行して閉じた場合は戻さない(クラスノードの親ファイルが変わるため)

### 白紙設計モード

`BlankDesignView` も同じ `CodebaseCanvas` を使っているので、追加の作業なしで同じメニューが出る。ストアは
`GameStoreContext` 経由で白紙設計用のものが使われるので、移動もそちらに効く。専用のE2Eは足さない。

## 4. TDD対象の純粋関数

### `moveClassTargets(codebase, classId): CodeFile[]`(`src/domain/codebase/moveClass.ts`)

`moveClass(codebase, classId, そのファイルID)` が成功するファイルの一覧を `codebase.files` の順で返す。

実装は `moveClass` と判定を二重に持たないこと(`moveMethod.ts` / `moveField.ts` の `targetError` と同じく、
`same-file` の判定を小さな関数に切り出して両方から呼ぶ)。`moveClass` の既存テストは変えずに通ること。

- 正常系: 移動元のファイル以外のファイルをすべて、`codebase.files` の順で返す
- 正常系: クラスが1つも無いファイルも含める
- 正常系: ファイルが移動元の1つだけなら `[]`
- 異常系: 存在しないクラスIDなら `[]`
- 元の `codebase` を変更しない

テストは `06-evaluation.md` の指摘5を踏まえ、上のケースを **1ケース1つの `it`** に分け、入力は各 `it` の Arrange で用意する
(Act の中で入力を分岐させない)。型は既存の `CodeFile` を使う。

application 層・ストアは変更しないので、新しいテストは不要。

## 未決事項

### 未決事項1: クラスのヘッダーのメニューで「別のファイルへ移動」をどこに置くか

- 選択肢A(推奨): 先頭に置く。ヘッダーの `aria-label` が「<クラス名> を別ファイルへ移動」で、ヘッダーの主目的が移動なので、メソッド/フィールドの「別のクラスへ移動」と同じ位置・同じ操作感(開いた瞬間に先頭へフォーカス → サブメニューが開く → Tab で候補)になる。そのかわり、ヘッダーを右クリックするたびに候補のサブメニューが開いた状態で表示される
- 選択肢B: 「クラスの名前を変更」の直後など、クラスに対する項目のまとまりの中に置く。今の先頭(「このファイルにクラスを追加」)とフォーカス位置は変わらないが、キーボードでは数回 Tab してから開くことになり、メソッド/フィールドのメニューと位置が揃わない

### 未決事項2: メソッド/フィールドのチップを右クリックしたときにも「別のファイルへ移動」(そのチップを持つクラスを移す)を出すか

- 選択肢A(推奨): 出さない。クラスのヘッダーを右クリックしたときだけにする。チップのメニューに「別のクラスへ移動」と「別のファイルへ移動」が並ぶと、どちらもチップ自身を動かすように読めて紛らわしい。チップのメニューは今のまま変わらない
- 選択肢B: 出す(「別のクラスへ移動」の直後)。クラスのヘッダーまで行かずに移せるが、移るのはチップではなくクラス全体であることをラベルで伝える工夫(「<クラス名> を別のファイルへ移動」など)が要る

### 未決事項3: 「新しいファイルへ移動」(`moveClassToNewFile`)も候補に入れるか

- 選択肢A(推奨): 入れない。前回「新しいクラスへ移動」を入れなかったのと揃える。余白へのドロップで既にでき、キーボードでも「ファイルを追加」→「別のファイルへ移動」で同じ結果にできる(YAGNI)
- 選択肢B: 候補の末尾に「(新しいファイル)」を足し、`moveClassToNewFile(classId)` を呼ぶ。1手で済むが、ファイル名が自動(`src/<クラス名>.ts`)になり、メソッド/フィールドのメニューと形が揃わない

### 未決事項4: 外側クリックで閉じたときのフォーカス復帰を、クリック先がフォーカスを取らなかったときだけにするか(`06-evaluation.md` の指摘1)

- 選択肢A(推奨): 今回含める。`dismiss` のフォーカス復帰を、rAF の中で `document.activeElement` が body(または null)のときだけ行うよう変える。メニューを開いたままサイドパネルの入力欄やステージの `<select>` をクリックしたとき、フォーカスが奪い返されなくなる。今回ヘッダーにも同じ復帰が効くようになるので、広がる前に直す。既存E2E「Escapeと外側クリックで開く前のチップにフォーカスを戻す」の外側クリック部分は「ステージの `<select>` にフォーカスが残る」に書き換え、「フォーカスを取らない場所(キャンバスの余白など)をクリックしたときはチップへ戻る」ケースを足す
- 選択肢B: 今回は含めない(今の挙動のまま)。別タスクで扱う
