# 03 ユーザ確定: インターフェース役を extends にすると「実装漏れ」の採点をすり抜ける抜け道を塞ぐ

- slug: `extends-interface-loophole`
- 元になった仕様草案: `docs/pipeline/extends-interface-loophole/02-draft-spec.md`

## 未決事項1: 抜け道をどこで塞ぐか

**確定: 選択肢A(採点で塞ぐ)**

`contract` の実装漏れが extends したインターフェース役も調べる(4.1)。`interfaceContracts.ts` とテストだけの変更で、操作・画面・E2E は変わらない。上級6の仕様の「操作ではなく状態で判定する」(`interface-segregation-stage.md` 231行目)と揃う。

## 未決事項2: 同じ上級6の「具象クラス ChatworkClient を extends して空実装を消す」抜け道(8手で100点の見込み)を今回扱うか

**確定: 選択肢A(今回は扱わず、別件として次の機能探索に回す)**

本件の仕様書に再現手順を残す。「extends の先祖が持っていれば実装漏れに数えない」は正当な使い方でもあり、「具象クラスを継承して別の実装を借りる」を見分ける新しいルールの設計が要るため。

## 未決事項3: 上級6の回帰テストをどこに置くか

**確定: 選択肢A(`advancedStages.test.ts`)**

`describe('advanced-interface-segregation')` の末尾に1件足し、点数と内訳(`contract` 5件で50点)まで確かめる。進行中の件と衝突しない。

## 未決事項4: extends の途中のクラス(`C extends B extends I` で B が契約の一部を持たず、子の C が持つ)を実装漏れに数えるか

**確定: 選択肢A(数える)**

B を実装漏れにする。今の implements 側の規則「自分と extends の先祖のどれかが持てばよい」と同じ向きで、規則が最小。抽象クラスを表す項目が無いので「途中のクラスは抽象だから持たなくてよい」を表せない、という手抜きを `// ponytail:` コメントで残す。

## 実装者への申し送り

未決事項1〜4すべて推奨案(A)が選ばれたため、`02-draft-spec.md` の本文(1章〜7章)に書かれた内容をそのまま実装の正本とする。追加の分岐・条件は無い。

未決事項2により、「具象クラスへの継承で実装を借りる」抜け道(1章に再現手順あり)は本件のスコープに含めない。将来の機能探索フェーズが対象にする際は、02-draft-spec.md 1章の再現手順を出発点にすること。
