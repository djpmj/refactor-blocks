# 機能案のブレスト

## 2026-10-10

### 1. Observerパターンのステージ

- 概要: 注文確定のたびに在庫・メール・ポイント付与クラスを直接呼んでいる状態を、通知の購読(Observer)に組み替えるステージ。
- 対象プレイヤーへの効果: 「呼ぶ側が呼ばれる側を知らない」依存の逆転と、通知先を足しても元クラスを触らずに済む感覚を体験できる。

### 2. Stateパターンのステージ

- 概要: 注文の状態(未払い・発送済み・キャンセル)ごとのif/switchが各メソッドに散らばったクラスを、状態クラスへ分けるステージ。
- 対象プレイヤーへの効果: StrategyやTemplate Methodとの違いを比べながら、状態遷移を持つ処理の整理方法が身につく。

### 3. Decoratorパターンと横断的関心事のステージ

- 概要: ログ出力・キャッシュ・リトライが本来の処理に混ざっているクラスから、それらを包む層(Decorator)として外へ出すステージ。
- 対象プレイヤーへの効果: 本筋の責務と付随処理を分けると、組み合わせの自由度とテストしやすさが上がることを実感できる。

### 4. Long Parameter List / Parameter Objectステージ

- 概要: 引数が6個以上あるメソッドを、引数オブジェクトにまとめる操作と、引数の数による減点ルールを追加する。
- 対象プレイヤーへの効果: 一緒に動く引数は1つの概念だと気づき、呼び出し側の変更が減る様子を変更依頼で確かめられる。

### 5. Singleton・グローバル状態の解消ステージ

- 概要: あちこちから `Config.instance` を直接参照している構成を、コンストラクタ注入に組み替えるステージ。
- 対象プレイヤーへの効果: 隠れた依存が結合度とテストのしにくさを生むことを、依存矢印の増減で目に見えて学べる。

### 6. デッドコード検出と削除ステージ

- 概要: どこからも呼ばれないメソッドやクラスをキャンバス上で薄く表示し、削除すると行数と保守コストが減ることを体験させる。
- 対象プレイヤーへの効果: 「足す」だけでなく「消す」ことも改善だと知り、呼び出し関係を読む習慣がつく。

### 7. 手数チャレンジ(最小手順スコア)

- 概要: 同じ到達形に何手で届いたかを記録し、より少ない操作で達成した場合に別枠で称号を出す。
- 対象プレイヤーへの効果: 無駄な往復を避けて最短の分解手順を考える視点が育ち、リプレイの再挑戦動機にもなる。

### 8. Undo / Redo操作

- 概要: 抽出・移動・統合などの操作を履歴として積み、Ctrl+Z / Ctrl+Shift+Zで戻したり進めたりできるようにする。
- 対象プレイヤーへの効果: 失敗を恐れず試行錯誤でき、「この一手で採点がどう変わったか」を前後比較で学べる。

### 9. 依存グラフの自動整列ボタン

- 概要: ファイルやクラスの配置を依存の向き(上位→下位)に沿って自動レイアウトするボタンを足す。
- 対象プレイヤーへの効果: 矢印が上へ戻る箇所が一目で分かり、層構造の崩れや循環依存に気づきやすくなる。

### 10. Null Objectパターンのステージ

- 概要: あちこちで `if (x == null)` を書いている呼び出しコードを、何もしない既定の実装(Null Object)に置き換えるステージ。
- 対象プレイヤーへの効果: 条件分岐を呼び出し側から消す多態の使い方と、nullチェック漏れというバグの根を減らす考え方を学べる。

## 2026-10-03

### 1. Adapterパターンのステージ

- 概要: 外部ライブラリ(メール送信SDKなど)の呼び出しがドメインのあちこちに散らばっている状態を、自前のインターフェース+Adapterに閉じ込めるステージ。
- 対象プレイヤーへの効果: 外部仕様の変更から自分のコードを守る「腐敗防止層」の考え方と、依存の向きの整理を体験できる。

### 2. Facadeパターンのステージ

- 概要: 呼び出し側が5つのクラスを順番に呼んで1つの処理を実現している状態を、窓口クラス1つにまとめるステージ。
- 対象プレイヤーへの効果: 結合度を下げる「窓口を作る」手段と、まとめすぎ(神クラス化)との境目を考えられる。

### 3. Mediatorパターンのステージ

- 概要: 画面部品どうしが互いを直接参照し合う網目状の依存を、仲介役クラス経由に組み替えるステージ。
- 対象プレイヤーへの効果: 多対多の依存を多対一に減らす発想と、循環依存の解消の別の方法を学べる。

### 4. Law of Demeter(メッセージチェーン)ステージ

- 概要: `a.getB().getC().doX()` のような他人の内部を辿る呼び出しを、委譲メソッドで隠すステージと、チェーンの長さの減点ルール。
- 対象プレイヤーへの効果: 「知りすぎ」が結合を生むこと、Tell, Don't Askとの関連を実感できる。

### 5. Pull Up / Push Down(メソッドの上げ下げ)操作

- 概要: 継承階層で、子クラスに重複したメソッドを親へ引き上げる、または一部の子しか使わない親のメソッドを子へ押し下げる操作を追加する。
- 対象プレイヤーへの効果: 継承階層の中での置き場所の判断(重複排除と過剰な共通化のバランス)を練習できる。

### 6. Inline Method / Inline Class(逆向きの操作)

- 概要: 薄すぎる委譲だけのメソッド・クラスをインライン化して消す操作と、それが正解になるステージ。
- 対象プレイヤーへの効果: 分けるだけでなく「戻す」判断も設計の一部だと知り、やりすぎ検知と対で理解できる。

### 7. 命名の採点とリネーム操作

- 概要: `process` `doIt` `data2` のような曖昧な名前を検出して減点し、ブロックの名前を変えるリネーム操作と「責務が伝わる名前にする」ステージを用意する。
- 対象プレイヤーへの効果: 分割の質は名前に表れることに気づき、責務をひと言で言えるかの確認習慣がつく。

### 8. 変更ホットスポットのヒートマップ

- 概要: 変更依頼を複数回出したとき、何度も触られたブロックを色の濃さで表示する。
- 対象プレイヤーへの効果: 変更が集中する場所(変更理由の混在)を可視化し、Shotgun SurgeryやDivergent Changeの兆候に気づける。

### 9. AI講評への「なぜ?」ソクラテス式質問モード

- 概要: 講評をいきなり答えとして出さず、「このクラスの変更理由はいくつありますか?」のように問い返し、プレイヤーの回答を受けて講評を深める。
- 対象プレイヤーへの効果: 指摘を受け身で読むのでなく、自分で言語化して設計の根拠を説明する力が育つ。

### 10. ステージのエクスポート/インポートと自作ステージ共有

- 概要: 白紙設計モードで作った構成やステージ定義をJSONで書き出し・読み込みでき、チームの勉強会で自作の題材を配れるようにする。
- 対象プレイヤーへの効果: 実務で見たコード臭を題材にでき、チームでの設計議論や勉強会の教材として使える。
