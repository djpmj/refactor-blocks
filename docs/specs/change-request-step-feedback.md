# change-request-step-feedback: 変更依頼は1件ごとに答え合わせし、その場で置き直せるようにする

## 背景・目的

2026-10-17 に初級2の変更依頼(3件)に挑戦して、依頼1の部品を描画のクラスではなく `InvoiceService` に置いたが、
「実装を終える」を押すと**何も言われずに**依頼2へ進んだ。間違いに気付けたのは、3件すべて終えたあとの「変更依頼の結果」の画面だった。

- 結果を見たときには依頼1の操作から時間がたっていて、「なぜそこに置いたか」を思い出しにくい
- 置き直して確かめる手段が無い(「もう一度挑戦」で3件すべてやり直すしかない)
- 依頼1の置き間違いは、依頼2・3のコードにも積み重なる

クラス設計を身につけるには、「置いた → 理由つきで良し悪しが分かる → 置き直して違いを見る」を1件ずつ回せる方がよい。

## 変更対象ファイル一覧

| 種別 | パス | 層 | 役割 |
| --- | --- | --- | --- |
| 変更 | `src/presentation/store/useGameStore.ts`(`finishImplementation` まわり) | presentation | 「実装を終える」で、その依頼の結果を出す段階(`reviewing`)を挟む。「置き直す」で、その依頼を始めた時点のコードに戻す |
| 変更 | `src/presentation/change/ChangeRequestPanel.tsx` | presentation | 1件分の結果カード(今の結果画面の1件分と同じ中身)と、`置き直す`・`次の依頼へ` のボタンを出す |
| 変更 | 変更依頼の E2E(`e2e/` の change-request 系) | E2E | 新しい流れに合わせ、下の受け入れ基準を確かめる |

`domain` / `application` は変更しない(1件分の評価は今の `evaluateImplementationUseCase` をそのまま使う)。

## データ・型の変更

- `ChangeSession` に `reviewing: ChangeOutcome | null` を足す。`null` のときは部品を置いている途中、値があるときはその依頼の結果を見ている途中
- `置き直す` を押したら、`outcomes` からその依頼の結果を取り除き、コードを `carried`(その依頼を始めた時点)+ 部品置き場に戻す
- 元に戻す(Ctrl+Z)の履歴は、依頼を始めた時点からに限る(今と同じ)

## 流れ

1. 部品を置いて「実装を終える」を押す
2. その依頼の結果カードを出す(置き方の点数・解答例・減点の理由・「解答例の図を見る」。今の結果画面の1件分と同じ)
3. ボタン:
   - `置き直す`: その依頼を最初からやり直す(何度でもよい)
   - `次の依頼へ`(最後の依頼では `結果を見る`): 今の結果を確定して進む
4. 全件終えたら、今と同じ「変更依頼の結果」(全件のまとめ)を出す。まとめには、各依頼について確定した結果だけを使う
- 1件分の結果カードでは、点数の見出しを「この依頼の置き方 <点>点」にする(全体の平均と混ざらないように)

## TDD対象の純粋関数

`domain` / `application` に新しいロジックは無い。ストアの状態遷移はストアの既存のユニットテスト(`useGameStore.test.ts`)に足す。

- 「実装を終える」で `reviewing` に結果が入り、`index` はまだ進まない
- `置き直す` で `reviewing` が `null` に戻り、コードがその依頼の開始時点に戻る
- `次の依頼へ` で `outcomes` に結果が足され、`index` が1進む

## 受け入れ基準

1. 初級2で変更依頼に挑戦し、依頼1の部品を `InvoiceService` に置いて「実装を終える」を押すと、依頼2へ進まずに依頼1の結果カード(置き方 90点、解答例 `InvoicePdfRenderer`)が出る
2. `置き直す` を押して `InvoicePdfRenderer` に置き直すと、依頼1の結果が置き方 100点になる
3. `次の依頼へ` で依頼2へ進み、3件終えると全体の結果が出て、依頼1は置き直したあとの結果になっている
4. `npm run check` と `npm run test:e2e` が通る

## スコープ外

- 置き方の採点の変更
- 解答例の求め方(`change-request-sample-on-ideal-base` で扱う)
