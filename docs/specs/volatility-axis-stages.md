# 中級4・中級5: 変わる場所しだいで正解が変わるステージ

## 背景・目的

今あるステージでは、責務ごとに分ければ正解になる。そのためプレイヤーは「とりあえず全部分ける」と覚えてしまいやすい。
実務の設計判断の核は、**変わりやすい所を閉じ込める**ことにある。コードだけを見ても正解は決まらず、
要求(どこがよく変わるか)で決まる。

この体験をさせるために、**同じ初期コード**で「よく変わる場所」だけが違う2ステージを追加する。

- 中級4: 税の計算ルールが毎月のように変わる → 税の計算を別クラスへ出すのが正解
- 中級5: 帳票の出力形式がよく変わる → 帳票の整形を別クラスへ出すのが正解

どちらのステージでも、構造の採点(`scoreCodebase`)だけならどちらの分け方でも100点になる。差が出るのは
変更依頼の結果(変更容易性スコア)だけ。これは設計どおりの挙動で、「コードの形だけでは良し悪しは決まらない」ことを
テストでも固定する。

**ponytail**: ステージのデータと模範解答を足すだけで作る。ドメインのロジックは変えない。
クリア判定(✅)に変更容易性を入れるかは未決事項に回す。

## データ/型の変更

型の変更はない。

### 共通の初期コード(`salesReportCodebase` などの定数にして、2ステージで共有する)

`src/report/SalesReportService.ts` にクラス `SalesReportService` を置く。受け皿のクラスは用意しない
(プレイヤーが自分で「クラスを追加」する)。

| メソッド(public) | 処理(行数, responsibility) | 行数(+2) |
| --- | --- | --- |
| `generateMonthlyReport` | 売上を集計する(40, `aggregation`)/ 税額を計算する(30, `tax`)/ 帳票の形式に整形する(30, `formatting`) | 102 |
| `generateQuarterlyReport` | 売上を集計する(36, `aggregation`)/ 税額を計算する(28, `tax`)/ 帳票の形式に整形する(28, `formatting`) | 94 |

- 呼び出し元として `src/report/ReportController.ts` に `ReportController.downloadReport`(public)を置く:
  帳票を作って返す(55行, `http`, uses: 両方の generate メソッド)。
  55行と大きくしているのは、よく変わる処理を持った generate* を `ReportController` へ持ち上げる近道を、
  変更時の上限超えで塞ぐため(処理が1つなので抽出して逃げることもできない)。
  これがないと、「税を `SalesReportService` に残し、集計と整形を外へ出す」解き方だけ波及の減点を受けず、
  模範解答より高くなる(評価フェーズで判明)
- `tax` と `formatting` の行数は**必ず同じ**にする。どちらを残しても `SalesReportService` の大きさが同じになり、
  構造の採点に差が出ないようにするため
- 各処理には `suggestedName` を付ける(例: `calculateMonthlyTax` / `formatMonthlyReport`)

### ステージの数値(2ステージ共通)

- `limits: { method: 60, class: 150, file: 300 }`、`dependencyLimit: 1`、`responsibilityLimit: 2`
- この組み合わせで、プレイヤーは次のように誘導される
  - メソッド60行: 税・整形の**両方**をメソッドに抽出しないと、元のメソッドが上限を超える
  - 責務2種類: `SalesReportService` には集計ともう1つしか残せない
  - 依存1本: 抽出したメソッドを2つの別クラスへ出すと、`SalesReportService` の依存先が2つになり減点される
  - つまり「両方を抽出し、**片方だけ**を1つの新しいクラスへ移す」ことになり、どちらを移すかがプレイヤーの判断になる

### 中級4

- id: `intermediate-volatile-tax`、title: `中級4: 変わるのは税の計算`
- description: 売上帳票を作る `SalesReportService`。経理から「税の計算ルールは法改正や社内規定で毎月のように変わる」
  と聞いている。帳票の見た目はここ3年変わっていない、と分かる文にする
- goal: 行数・責務・依存の上限と、「よく変わる所を1つのクラスに閉じ込めよう」
- changeRequests(2件とも `tax`、`linesPerSite: 14`): 例「軽減税率の対象品目を増やして」「税額の端数処理を変えて」

### 中級5

- id: `intermediate-volatile-format`、title: `中級5: 変わるのは帳票の形式`
- description: 中級4と**同じコード**だと明記する。営業から「取引先ごとに帳票の形式(列の並び・PDF/CSV)を変えてほしい
  という依頼が毎月来る」と聞いている。税の計算はここ数年変わっていない、と分かる文にする
- goal: 中級4と同じ
- changeRequests(2件とも `formatting`、`linesPerSite: 14`): 例「取引先向けに列の並びを変えて」「PDFでも出せるようにして」

### `linesPerSite: 14` の理由

変更の行数は、変更箇所2つ × 14 = +28行になる。以下の計算は `METHOD_OVERHEAD_LINES` / `CLASS_OVERHEAD_LINES` を含む。

| 解き方 | 変更が入るクラス | 変更前 → 変更後 | 上限150 |
| --- | --- | --- | --- |
| 正解(よく変わる方を移す) | 新しいクラス | 64 → 92 | 超えない |
| 逆(変わらない方を移す) | `SalesReportService` | 148 → 176 | **超える** |
| 両方を1つのクラスへ移す | 何でも入ったヘルパー | 126 → 154 | **超える** |

変更容易性スコアの実測値は、初期 45点、正解 95点、逆 85点、両方1クラス 85点。
正解でも、依存元の `SalesReportService` への波及で -5点になる。逆の分け方は上限超え -10点に加え、
`ReportController` への波及 -5点も受ける。

「税だけを `SalesReportService` に残し、集計と整形を外へ出す」解き方も100点で、変更容易性も95点になる。
よく変わる所が1クラスに閉じているので、**もう1つの正解として認める**。数値を調整してもよいが、
下の受け入れ基準の大小関係は必ず守ること。

## 模範解答(`sampleAnswer.ts`)

- `intermediate-volatile-tax`
  1. 2つのメソッドから、`tax` と `formatting` の処理をそれぞれ抽出する(合計4回)
  2. `addClass: { name: 'TaxCalculator', file: 'src/report/SalesReportService.ts' }`
     (ファイルを分ける手順は必須ではない。ファイル上限300に収まる)
  3. 抽出した税計算のメソッド2つを `TaxCalculator` へ移す
- `intermediate-volatile-format`: 同じ手順で、移す先を `ReportFormatter` にし、移すのを整形のメソッド2つにする

## TDD対象

ロジックの追加はない。ステージの性質を `volatilityStages.test.ts` でテストする(AAAパターン)。
既存の `stageCatalog.test.ts` の `describe.each` が全ステージに自動で当たる。そのため「80行以上のメソッドがある」
「初期は減点」「模範解答で100点」「変更容易性が上がる」「影響クラス数が増えない」は、新しいテストを書かなくても確かめられる。

`volatilityStages.test.ts` のケース:

1. 2ステージの初期コードは等しい(`toEqual`)
2. 中級4の模範解答(税を移す)と中級5の模範解答(整形を移す)は、**どちらのステージの `scoreCodebase` でも100点**になる。
   コードの形だけでは差がつかないことを固定する
3. 中級4では、税を移した解答の変更容易性スコア > 整形を移した解答の変更容易性スコア
4. 中級5では、3の逆が成り立つ
5. 各ステージで、税と整形を1つのクラスへ移した解答の変更容易性スコアは、模範解答より低い
   (「何でもヘルパー」に逃げても得をしない)
6. 各ステージで、よく変わる処理だけを残して集計ともう片方を外へ出す解答は100点で、変更容易性は模範解答を上回らない
   (ヒントの答えが最善であり続けることを固定する)
7. 各ステージで、よく変わる処理を持った generate* を `ReportController` へ持ち上げる解答は、変更容易性が模範解答より低い

変更容易性スコアは、`stageCatalog.test.ts` の `changeReadiness` と同じく
`averageScore(changeRequests.map(r => scoreChange(measureChange(...))))` で計算する。
共通化したくなっても、テスト用の小さなヘルパーを複製するだけでよい。

## 未決事項

- **波及の採点は「呼ばれている側」にしか付かない**。依存グラフの頂点(誰からも呼ばれないクラス)によく変わる処理を
  置くと、波及の減点を受けない。このステージでは `ReportController` を大きくして数値で塞いだが、根本的な対策は
  採点ルール(`measureChange` の ripple)の見直しになる。今後のステージでも同じ近道が出ないか、評価フェーズで確かめる

- **逆の分け方でも ✅(100点)が付く問題**。構造の採点しか進捗に記録しない(`recordProgress`)ため、
  逆の分け方でもクリア扱いになる。変更依頼の結果で差は見せるものの、クリア表示と食い違う。
  対応するなら「このステージは変更容易性スコアも満点でないと ✅ にしない」といった、別の小さな仕様になる。
  ステージを遊んでもらってから判断する
