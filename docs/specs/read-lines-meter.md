# 変更のために「読む行数」を見せる(長いメソッドのなぜ)

> **前提**: `why-split-change-pain`(Issue #60)のマージ後に実装する。`src/domain/change/changePain.ts`(`PainSummary` / `measurePain`)と
> `ChangePainCard` に足す形で作る。#60 が未マージなら、先にそちらを完了させる。

## 背景・目的

「メソッドが長いとなぜだめか」が、プレイヤーに伝わっていない。行数の上限(50行など)は「ルール」として示されるだけで、
**長いと何が困るのか**を体験する場所が無い。

実務で長いメソッドが困るのは、変更や不具合調査のたびに**その全体に目を通さないと、どこを直せばよいか分からない**から。
#60 の変更の痛みカードは「直す場所が何か所か」を見せるが、「そこを直すために**何行読む必要があるか**」は見せていない。
1か所でも、その1か所が120行のメソッドの中なら、120行を読む羽目になる。

変更の痛みカードに、**読む行数**を足す。分けていくと「120行 → 12行」のように、長いメソッドを分ける効果が数字で見える。

## 見た目・内容の仕様

`ChangePainCard` の「直す場所は今 N か所(M クラス・K ファイル)」の次の行に足す。

**100点になるまで**

- 「**その場所を直すために、目を通す行数は今 L 行**」(`<strong>` で強調)
- 初期から減っているときは「(最初は Q 行でした)」
- 直す場所の一覧は、各行の末尾に、そのメソッドの行数を添える(`クラス名.メソッド名(120行)`)。一番長いメソッドが分かる

**100点になったら**

- 手間が減っていれば(`improved`)、既存の「P か所 → N か所」の行に加えて、**読む行数が減っていれば**「読む量は **Q 行 → L 行**」を出す。
  減っていなければ、この行は出さない(嘘の改善は出さない)
- `why` の文章・サイドバーの自動オープンは #60 のまま変えない

行数の言葉は、プレイヤーが見慣れている画面上の行数(メソッドチップの表示、`methodLines`)と同じ数え方にする。

## データ・型の変更

`src/domain/change/changePain.ts` の `PainSummary` に追加:

```ts
export type PainSummary = {
  // …既存(siteIds / classes / files)
  /** 変更箇所のメソッドの行数(`methodLines`)の合計。同じメソッドは1回だけ数える。 */
  readonly readLines: number;
};
```

`ChangePain.improved` の判定は、#60 の「変更箇所の数 → クラス数・ファイル数」に、**読む行数が小さくなっていれば true** を加える
(どれか1つでも減っていて、増えているものが無い、という扱いにはしない。#60 の定義を「どれかが減れば true」に素直に広げるだけにする)。

`// ponytail: 「読む行数」は変更箇所のメソッドの行数の合計で近似する(クラスの全体や、呼び出し元は数えない)。実際の理解の手間とずれると分かったら、呼び出し元・同じクラスの関係メソッドも足す`

## TDD対象の純粋関数

### `measurePain`(追加分)

1. 変更箇所が1メソッド(処理50行)なら `readLines` は `methodLines` の値(50 + `METHOD_OVERHEAD_LINES`)
2. 変更箇所が2メソッドなら、2つの `methodLines` の合計
3. 1つのメソッドが複数の依頼の責務の処理を持っていても、同じメソッドは1回だけ数える
4. 長いメソッドから、依頼の責務の処理だけを小さなメソッドへ抽出したコード(テストで組み立てる)では、`current.readLines` が `initial.readLines` より小さく、`improved` が `true`
5. 変更箇所の数・クラス数・ファイル数が同じでも、`readLines` が小さければ `improved` は `true`
6. 今のコード = 初期のコードなら `improved` は `false`(既存の期待を維持)

## 受け入れ基準

- `npm run check` が通る
- `npm run test:e2e` が通る
- 長いメソッドがあるステージ(例: チュートリアル1)で、カードに「目を通す行数は今 L 行」が出て、一覧の各メソッドに行数が付く
- 長いメソッドから処理を抽出して分けると、L が減り「(最初は Q 行でした)」が出る
- 100点になったとき、読む行数が減っていれば「Q 行 → L 行」が出る。減っていないステージではこの行は出ない
- 行数の数え方が、メソッドチップに表示される行数と一致する
- #60 の既存の表示・挙動(`why`・サイドバーの自動オープン・「P か所 → N か所」)が変わらない

## スコープ外

- メソッドの中身を実際に読ませる・クイズにする(「バグを探せ」のような体験)
- 呼び出し元・同じクラスの関係メソッドまで含めた読む量の計算
- 認知的複雑度・ネストの深さの表示
- キャンバス上のメソッドチップに読む行数を出すこと(チップには既に行数がある)
- 行数の上限・採点の変更
