# toolbar-answer-menu: ツールバーの参考・答えをメニューにまとめ、答えの前にヒントを勧める(あわせてチュートリアル1の課題文を直す)

## 背景・目的

実際に遊んで見つかった、遊びやすさの問題を2つ直す。

### 1. チュートリアル1の「困っていること」が別のステージの文

チュートリアル1(`tutorial-extract-method`、売上レポートの `ReportService.printMonthlyReport`)の `problem` が、
`'placeOrderに検証と保存がまとまっている'` になっている(チュートリアル2の内容)。
最初に遊ぶステージで課題とコードが食い違い、何を直せばよいか混乱する。

### 2. ツールバーのボタンが8個横並びで、答えがすぐ押せる

キャンバスの上のツールバー(`StagePanel` の `ActionToolbar`)に、次の8個が同じ重さで並んでいる。

- 変更依頼に挑戦・元に戻す・やり直し・最初に戻す・変更前の図を見る・解答例の図を見る・解答を再生・操作ガイド

この並びには2つの問題がある。

- どれを押せばよいか迷う
- 「解答例の図を見る」「解答を再生」が普段の操作の隣にあり、考える前に答えを見てしまいやすい。
  自分で気づくことが学びの中心なので、答えはヒントより奥に置きたい

そこで、「変更前の図を見る」「解答例の図を見る」「解答を再生」を **「参考・答え ▾」メニュー**にまとめる。
さらに答え(解答例の図・解答を再生)を開く前に、**先にヒントを試すよう勧める確認**を挟む。

## データ・型の変更

なし。答えの確認を済ませたかどうかは、`ReferenceMenu` の中の状態(`useState`)で持つ。
ステージを切り替えたら確認し直す(呼び出し側で `key={stage.id}` を付ける。今の `PreviewButtons` と同じ)。保存はしない。

## 見た目・動きの仕様

### 1. チュートリアル1の課題文

- `problem` を `'printMonthlyReportに集計・計算・表の組み立て・出力がまとまっている'` にする

### 2. ツールバー

- ツールバーの並びは、左から次の6つにする
  1. 変更依頼に挑戦(今のまま、`button--primary`)
  2. 元に戻す
  3. やり直し
  4. 最初に戻す
  5. **参考・答え ▾**(新規)
  6. 操作ガイド
- 「参考・答え ▾」は、今の `PreviewButtons` と同じ条件で無効にする(変更依頼に挑戦している間)

### 「参考・答え ▾」メニュー(`ReferenceMenu`)

- ボタン(`data-testid="reference-menu-button"`、`aria-haspopup="menu"`、`aria-expanded`)を押すと、ボタンの下にメニュー(`role="menu"`)が開く
- 項目(`role="menuitem"`)は次の3つ。区切り線で「参考」と「答え」を分ける
  - 参考
    - `変更前の図を見る`(`data-testid="reference-before"`): 今と同じく変更前の図を開く。確認は挟まない
  - 答え(見出しに小さく「答え(ネタバレ)」)
    - `解答例の図を見る`(`data-testid="reference-sample"`): 確認を挟んでから、今と同じく解答例の図を開く
    - `解答を再生`(`data-testid="reference-replay"`): 確認を挟んでから、今と同じく解答の再生を開く
  - 解答例が未登録のステージでは、答えの2項目を無効(`aria-disabled="true"`)にし、`title` は今と同じ「このステージには解答例が未登録です」
- 閉じ方: 項目を選ぶ・Esc・メニューの外側をクリック・もう一度ボタンを押す。Esc で閉じたらボタンにフォーカスを戻す
- キーボード: 開いたら最初の有効な項目にフォーカスする。↑↓で項目を移動し、Enter / Space で選ぶ。
  既存の右クリックメニュー(`CanvasContextMenu`)の作りを参考にし、新しい依存は足さない

### 答えの前の確認ダイアログ

- 答えの項目を選んだとき、そのステージでまだ「答えを見る」を選んでいなければ、ネイティブの `dialog`(`data-testid="answer-confirm"`、`showModal()`)を開く
- 見出し: `答えを見ますか?`
- 本文: `答えを見ると、自分で気づく機会がなくなります。先にヒントを1つ見てみませんか?`
  - 残りのヒントがある場合、`ヒントはあと N 個あります`(N = 全ヒント数 − 開いたヒント数)を添える
- ボタン(この順。最初のボタンにフォーカス)
  1. `ヒントを見る`(`button--primary`): ダイアログを閉じ、ヒントを1つ開く(今のサイドバーの「ヒントを見る」と同じ処理)。
     サイドバーが閉じていたら開く。残りのヒントが無いときは表示しない
  2. `答えを見る`: ダイアログを閉じ、選んだ答え(解答例の図/解答を再生)を開く。以後、そのステージでは確認を挟まない
  3. `やめる`: ダイアログを閉じるだけ。Esc も同じ
- ダイアログを閉じたら、フォーカスは「参考・答え ▾」ボタンに戻す(答えを開いた場合は、開いた図・再生のダイアログに任せる)

## TDD対象の純粋関数

なし(表示とステージ定義の文言の変更)。ステージ定義の誤りは、次のカタログのテストで防ぐ。

### ステージカタログ(`stageCatalog.test.ts`)

- リファクタリングの全ステージで、`problem` が、そのステージの初期コード(`stage.codebase`)にあるクラス名・メソッド名のどれかを含むか、
  クラス名・メソッド名をまったく含まない(一般的な言い回し)こと。
  言い換えると、`problem` に出てくるコードの識別子らしい語は、すべてそのステージのコードにあるクラス名・メソッド名であること
  (今回のように、別のステージのメソッド名を書いてしまう誤りを防ぐ)
  - 「識別子らしい語」は、小文字と大文字の切り替わりを含む英字の語(`/\b[a-z]+[A-Z][A-Za-z0-9]*\b|\b[A-Z][a-z]+[A-Z][A-Za-z0-9]*\b/g`)とする。
    `API` のような大文字だけの略語は対象にしない(今ある `'注文APIに…'` を誤検出しないため)

## 受け入れ基準

1. チュートリアル1の「困っていること」が `printMonthlyReport` についての文になっている
2. カタログのテストで、`problem` に別のステージの識別子が入っていると失敗する(今の誤りのままだと失敗し、直すと通る)
3. ツールバーのボタンが「変更依頼に挑戦・元に戻す・やり直し・最初に戻す・参考・答え ▾・操作ガイド」の6つになっている
4. 「参考・答え ▾」から「変更前の図を見る」を選ぶと、確認なしで変更前の図が開く
5. 「解答例の図を見る」を選ぶと確認ダイアログが出る。「ヒントを見る」を押すとダイアログが閉じてヒントが1つ増え、解答例は開かない
6. 確認ダイアログで「答えを見る」を押すと解答例の図が開く。同じステージでもう一度答えの項目を選ぶと、確認なしで開く。ステージを切り替えると、また確認が出る
7. メニューはキーボードだけで開閉・選択でき、Esc で閉じるとボタンにフォーカスが戻る
8. 解答例が未登録のステージでは、答えの2項目が無効になっている
9. 既存の E2E(変更前の図・解答例の図・解答の再生を開くもの)は、メニューと確認ダイアログを通す手順に直して通る
10. `npm run check` と `npm run test:e2e` が通る

## スコープ外

- 抽出すると行数が増えて悪くなったように見える問題(別の仕様で扱う)
- 何も選んでいないときの右パネルの幅(別の仕様で扱う)
- ヒントの中身・数の変更
- 答えを見たことの採点への反映や記録
- 「元に戻す」「やり直し」「最初に戻す」のまとめ直し
