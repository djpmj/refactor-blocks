# comparison-quiz-no-giveaway: 設計くらべで、答える前に答えが透けて見える表示をなくす

## 背景・目的

2026-10-17 に設計くらべ1問目「メールの文面を変えるなら」を開くと、考える前に答えが分かってしまった。

1. **設計名が評価を含む**: 設計Bの名前が `UserController が全部やっている設計` で、「全部やっている」が悪い設計だと言っている。
   設計Aは `DBは UserRepository、メールは Mailer に任せた設計`。2〜4問目の名前(`帳票の整形を ReportFormatter に分けた設計` など)は中立な説明なので、1問目だけ浮いている
2. **答える前から警告色が出る**: 設計Bの `registerUser()`・`deleteUser()` が、行数の上限超えの赤枠で表示される(プレビューに `methodLimit` を渡しているため)。赤い方を避ければ正解できる
3. **設計Bに空のクラスがある**: 設計Bはステージの初期コードそのものなので、受け皿として置いた空の `UserRepository`・`Mailer`(`メソッドなし`)が並ぶ。「全部やっている設計」の説明と合わず、「中身を入れるべき箱が空いている」ことも答えのヒントになる

## 変更対象ファイル一覧

| 種別 | パス | 層 | 役割 |
| --- | --- | --- | --- |
| 変更 | `src/infrastructure/quizzes/comparisonQuizzes.ts` | infrastructure | 1問目の設計名を中立にする。設計のコードから、メソッドの無いクラス・クラスの無いファイルを取り除く |
| 変更 | `src/infrastructure/quizzes/comparisonQuizzes.test.ts` | infrastructure | 上のテスト |

`domain` は変更しない。

## データ・型の変更

なし。

## 仕様

- 1問目の設計名:
  - A: `保存は UserRepository、メールは Mailer に分けた設計`
  - B: `登録・保存・メール送信を UserController にまとめた設計`
- 設計のコードは、出題用に「メソッドが1つも無いクラス」と「クラスが1つも無いファイル」を取り除いてから出す(全問共通。取り除く処理は `comparisonQuizzes.ts` の中の小さな関数にする)
- プレビューの警告色(行数の上限超えの赤枠など)は、答える前は出さない。答えたあとは今どおり出し、解説と一緒に「どこが上限を超えるか」が見えるようにする
- 行数の上限の文(`行数の上限: メソッド17行・…`)は、答える前も今どおり出す(数字から自分で判断できるようにする)

## TDD対象の純粋関数

### `comparisonQuizzes.test.ts`(infrastructure)

- どの問題のどの設計にも、メソッドの無いクラスが無い
- 設計名に `全部` `だけ` `ひどい` などの評価の言葉が入っていない(禁止語の一覧で確かめる)
- 取り除いたあとも、変更依頼の変更箇所(`findChangeSites`)が見つかる

## 受け入れ基準

1. 1問目の設計Bの名前が `登録・保存・メール送信を UserController にまとめた設計` で、設計Bに `UserRepository`・`Mailer` の空のクラスが出ない
2. 答える前は、どちらの設計のメソッドにも赤枠が出ない。答えたあとは、設計Bの `registerUser()` などに赤枠が出る
3. 各問の正解・解説・点数は今と同じ
4. `npm run check` と `npm run test:e2e` が通る

## スコープ外

- 問題の追加・差し替え
- A・Bの左右の入れ替え(正解の偏りは既存のテストで守っている)
