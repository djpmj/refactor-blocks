# 左サイドバーで「もし、この変更が来たら?」をクリア条件より上に出す

## 背景・目的

左の「課題」サイドバー(`StagePanel.tsx` の `StageSidebar`)は、いま上から
「困っていること → クリア条件 → もし、この変更が来たら?(変更の痛みカード)」の順に並んでいる。
このゲームの流れは「まず変更を手で入れてみて痛みを知る → 組み替える → もう一度入れて楽になったのを確かめる」で、
プレイヤーが最初にやることは変更カードの「実際に直してみる」である。ところがカードがクリア条件の下にあるため、
クリア条件が長いステージではスクロールしないと見えず、何から始めればよいかが伝わりにくい。
変更カードをクリア条件の上に移し、「困っていること → もし、この変更が来たら? → クリア条件」の順にする。

## 変更対象ファイル一覧

### 変更

- `src/presentation/stage/StagePanel.tsx`(presentation): `StageSidebar` の描画順で、
  `ChangePainCard` と `ManualFixPanel`(調査中でないときだけ出す組)を `ClearConditionList` の前へ移す。
  - 並びは「ストーリー(`StoryIntro`)→ 前提ステージの案内(`PrerequisiteNote`)→ 困っていること →
    変更カード(`ChangePainCard`)→ 手で直す操作の案内(`ManualFixPanel`)→ クリア条件 → どんなコード? → (100点のときの各カード)」
  - `ManualFixPanel` は変更カードとひと続きなので、カードのすぐ下のまま離さない
  - 調査中(`investigating`)は従来どおり変更カードを出さず、「困っていること → クリア条件」になる
  - カードの見出しがステップで変わる(「もし、この変更が来たら?」「(もう一度)」「なぜ分けるのか」)のは従来どおりで、
    どのステップでも同じ位置(クリア条件の上)に出す
  - ステップが進んだときに変更カードへスクロールする既存の処理(`scrollToStepCard`)は変えない
- `e2e/sidebar-structure.spec.ts`: 「困りごと・クリア条件が上に並び…」のテストで、並び順を確かめるセレクタの順を
  `['.story-card', '.stage-panel__problem', '.change-pain', '.clear-conditions', '.stage-panel__description']` にし、
  テスト名も新しい並びに合わせる。先にこの期待を書き換えて失敗させてから実装する

## データ・型の変更

なし。

## TDD対象の純粋関数

なし(コンポーネントの並び替えのみ)。E2E `sidebar-structure.spec.ts` の並び順の期待を先に書き換えて Red にしてから、
`StagePanel.tsx` を直して Green にする。

## 受け入れ基準

1. チュートリアル1を開くと、左サイドバーが上から「困っていること → もし、この変更が来たら? → クリア条件 → どんなコード?」の順に並ぶ
2. 「実際に直してみる」を押して手で直している間の案内(`ManualFixPanel`)は、変更カードのすぐ下に出る
3. 組み替えたあと(もう一度直す・「なぜ分けるのか」)のステップでも、変更カードはクリア条件の上に出る
4. 変更依頼のないステージ・調査中の画面では、従来どおり「困っていること → クリア条件」と並ぶ
5. ステップが進んだときに変更カードが見える位置へスクロールする動き(`sidebar-flow-visibility`)が壊れない
6. `npm run check` と `npm run test:e2e` が通る(`change-pain`・`manual-fix`・`sidebar-flow-visibility`・`stage-flow` などの既存E2Eを含む)

## スコープ外

- 「困っていること」の位置の変更(先頭のまま)
- 変更カード・クリア条件の中身・見た目・折りたたみ方の変更
- 100点のときに出るカード群(`RoomToImproveNote` など)の並び
