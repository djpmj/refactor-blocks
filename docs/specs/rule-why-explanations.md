# 減点ごとの「なぜ?」解説

> **前提**: `score-jump-to-violations`(Issue #58)のマージ後に実装する。#58 が作る `ScoreBreakdown`(減点の内訳)の各項目に足す形で作る。

## 背景・目的

採点は「責務の混在 -20」「結合度 -10」のように**何がだめか**は示すが、**なぜだめか**を示さない。
プレイヤーは理由が分からないまま、減点を消すための作業をすることになり、「なぜ分けるのか」「なぜ長いとだめなのか」という疑問が残る。
ステージごとの「なぜ」(#60 の `why`)は題材に即した理由を100点で見せるが、**減点ルール(15種)そのものの理由**は、どこにも書かれていない。

#58 の「減点の内訳」の各項目に、**「なぜ減点?」**を開ける説明を足す。実務で起きる困りごとを1〜2文で見せ、ルールが「作業のための作業」でないことを伝える。
採点ロジック・点数・#58 のジャンプの挙動は変えない。

## 見た目・内容の仕様

### 「なぜ?」の開閉(`ScoreBreakdown`)

- 減点の内訳の各項目(項目名・件数・ジャンプのボタン)の横または下に、`なぜ?` ボタンを置く
  - ジャンプのボタン(#58 の `aria-pressed` トグル)とは**別のボタン**にする(ジャンプと開閉が混ざらないように)
  - `aria-expanded` と `aria-controls` で、説明のブロックと結ぶ
- 押すと、その項目の下に説明を開く。もう一度押すと閉じる。**複数の項目を同時に開いてよい**(開閉は項目ごと。ストアには持たず、コンポーネント内の状態でよい)
- 説明は `RULE_WHY[rule]` の2行:
  1. **こう困ります**(`trouble`): 実務で起きる困りごとを1〜2文
  2. **だから**(`because`): ルールが何を守るためのものかを1文
- キーボード(Tab・Enter/Space)で操作できる。説明は `<p>` で、色だけに頼らない
- 変更依頼の調査中(`changeSession !== null`)は、ジャンプと同じく内訳ごと無効のままでよい(「なぜ?」だけ有効にはしない。#58 の挙動のまま)

### `RULE_WHY` の文言(15ルール)

各ルールの `trouble` と `because`。実装者は文言を日本語として自然に整えてよい。**用語の説明ではなく「実際に何が困るか」を書く**こと、
解き方(どう直すか)は書かないこと(ヒントの領分)。

| ルール | こう困ります(`trouble`) | だから(`because`) |
| --- | --- | --- |
| `line-limit` 行数 | 長いメソッドは、どこを直せばよいか探すだけで全体を読むことになります。複数人が同じ場所を同時に直して、衝突もしやすくなります | 1か所を小さく保つと、読む量と衝突が減ります |
| `coupling` 結合度 | 呼んでいる先が多いほど、そのどれかが変わるたびに自分も壊れるおそれがあります。テストでも、呼び先の数だけ用意が要ります | 依存先を減らすと、変更の影響とテストの準備が小さくなります |
| `cycle` 循環依存 | AがBを、BがAを呼んでいると、片方を直すともう片方も直すことになり、どちらも単独でテスト・再利用できません | 依存を一方通行にすると、片方だけを安心して変えられます |
| `responsibility` 責務の混在 | DBの処理を直すつもりが、同じクラスのメール送信まで読み直すことになります。関係ない処理を壊すおそれもあります | 1つの理由で変わる処理だけをまとめると、変更の影響が1か所に収まります |
| `visibility` アクセス制御 | 外から呼べないはずのメソッドを別のクラスが呼んでいると、持ち主が中身を変えたとたんに、離れた場所が壊れます | 外に見せる範囲を絞ると、内側は自由に変えられます |
| `empty` 空のクラス・ファイル | 何も入っていないクラスやファイルは、読む人に「ここに何かあるはず」と探させ、時間を奪います | 使わないものを残さないと、コードの全体像が分かりやすくなります |
| `unused` 未使用のprivateメソッド | 誰も呼ばないメソッドは、消してよいのか分からないまま残り続け、読む量だけを増やします | 使われないコードを消すと、読む量が減り、勘違いも減ります |
| `lone-superclass` 子が1つだけの継承 | 子が1つしかない継承は、他にも子がいるはずだと読む人に探させます。使われない拡張ポイントを、ずっと保守することになります | 必要になってから継承を足すほうが、構造が分かりやすく保てます |
| `stub` 使わないメソッドの空実装 | 空のメソッドを呼ぶと、何も起きないか、例外になります。呼ぶ側は、動くものと動かないものを見分けられません | 役割ごとにインターフェースを分けると、持たない約束を背負わずに済みます |
| `contract` インターフェースの約束違反 | 約束(メソッド)を実装していないクラスを呼ぶと、実行時にはじめてエラーになります | 約束を守ると、呼ぶ側は中身を知らずに安心して使えます |
| `feature-envy` 他クラスのデータを触りすぎ | 他のクラスのデータばかり触るメソッドは、そのデータの持ち主が変わるたびに巻き込まれます | データと、それを使う処理を同じ場所に置くと、変更が1か所で済みます |
| `encapsulation` カプセル化の破れ | データを外から自由に書き換えられると、マイナスの残高のような不正な状態が作れ、どこで壊れたのか追えなくなります | データを持ち主だけが変えられるようにすると、不正な状態を入口で防げます |
| `cohesion` 凝集度が低い | 無関係なデータの塊が同居するクラスは、変更の理由が別々で、片方を直すともう片方に響きます | まとまりのあるデータと処理を1クラスにすると、変更が他へ漏れません |
| `trivial-method` 極小メソッドの量産 | 1〜2行のメソッドが何本も並ぶと、処理を追うのにあちこち飛び回ることになります | 分けるのは「ひと言で説明できるまとまり」ができるときだけにすると、読みやすさが保てます |
| `thin-class` 役割の薄い極小クラス | 小さな役割しかないクラスは、読む場所を増やすだけで、分けた得がありません | 分ける価値(変更理由が違う・使い回せる)があるときだけ分けると、全体が小さく保てます |

`lone-superclass` / `stub` / `contract` の説明は、実装時に既存の仕様書(`lone-superclass-scoring` / `interface-segregation-stage` /
`extends-interface-loophole`)の意図と矛盾しないか確かめる。矛盾する文言は仕様書側を正として直す。

## データ・型の変更

```ts
// src/presentation/stage/ruleWhy.ts
export type RuleWhy = { readonly trouble: string; readonly because: string };
export const RULE_WHY: Record<ScoreRule, RuleWhy>;
```

`Record<ScoreRule, …>` にすることで、将来 `ScoreRule` にルールを足したとき、説明の書き忘れが**型エラーで検出される**(`RULE_LABEL` と同じ)。

## TDD対象の純粋関数

なし(新しいロジックは無い。表示データのみ)。ただし次の小さなテストを書く(`ruleWhy.test.ts`)。

1. `RULE_WHY` の全ルール(`RULE_LABEL` のキー)について、`trouble` と `because` が前後の空白を除いて空でない
2. `RULE_WHY` のキー集合が `RULE_LABEL` のキー集合と一致する(ルールの追加漏れを検出する)

## 受け入れ基準

- `npm run check` が通る
- `npm run test:e2e` が通る(#58 のジャンプ・強調の既存E2Eが壊れない)
- 減点の内訳を開き、項目の「なぜ?」を押すと、`trouble`(こう困ります)と `because`(だから)が出る。もう一度押すと閉じる
- 「なぜ?」を押しても、ジャンプ(強調・画面への収め)は起きず、強調の状態も変わらない。逆に、ジャンプのボタンを押しても「なぜ?」の開閉は変わらない
- 複数の項目の「なぜ?」を同時に開ける
- キーボードだけで開閉でき、`aria-expanded` が正しく切り替わる
- 全15ルールに説明がある(型とテストで保証)。理由が用語の説明でなく、実際の困りごとになっている
- 採点・点数・`describeScore` の文言・#58 の既存の挙動が変わらない

## スコープ外

- ステージごとの理由(#60 の `why`)との統合・重複排除(2つは別物。ルールの理由と題材の理由)
- 理由の中の用語(SRP・DIPなど)の用語集・解説リンク
- 理由をAIで生成・補足すること
- 減点が無い(内訳に出ない)ルールの理由を一覧で見せること
- 白紙設計モード・設計くらべクイズの採点表示への適用
- 理由の多言語化・プレイヤーが編集できるようにすること
